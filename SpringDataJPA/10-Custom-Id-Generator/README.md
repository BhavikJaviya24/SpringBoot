# 10-Custom-Id-Generator

The capstone of the `SpringDataJPA` ID-generation series, moving beyond JPA's built-in strategies (`IDENTITY`, `SEQUENCE`, `TABLE`, `AUTO`, `UUID` from projects 07–09) to write a **fully custom ID generator** — producing IDs like `SBAI-4821` by combining a fixed prefix with a random number, using Hibernate's modern `@IdGeneratorType` mechanism.

## Overview

None of JPA's standard strategies can produce a prefixed, semi-readable identifier like `"SBAI-4821"` — that requires custom logic. This project builds that logic as a small reusable unit: a custom annotation (`@RnoId`) that a field can be marked with, backed by a Hibernate `IdentifierGenerator` implementation (`StudentRnoGenerator`) that actually produces the value at insert time.

## What it demonstrates

### `StudentRnoGenerator` — the actual generation logic
```java
public class StudentRnoGenerator implements IdentifierGenerator {
    String prefix;
    public StudentRnoGenerator(RnoId rnoId) {
        this.prefix = rnoId.name();
    }

    @Override
    public Object generate(SharedSessionContractImplementor session, Object object) {
        Random random = new Random();
        String rno = prefix + "-" + random.nextInt(1000, 9999);
        return rno;
    }
}
```
Implementing Hibernate's `IdentifierGenerator` interface means providing a `generate(...)` method that returns the value to use as the new entity's ID. Here, a constructor taking the custom `@RnoId` annotation captures the configured `prefix` (e.g. `"SBAI"`), and `generate(...)` concatenates that prefix with a random 4-digit number — producing IDs like `SBAI-4821`.

### `RnoId` — a custom annotation wiring the generator to the field
```java
@IdGeneratorType(StudentRnoGenerator.class)
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.FIELD})
public @interface RnoId {
    public String name() default "TCA";
}
```
`@IdGeneratorType(StudentRnoGenerator.class)` is Hibernate's mechanism (introduced as the modern replacement — see below) for declaring "any field annotated `@RnoId` should have its ID generated by `StudentRnoGenerator`." The annotation itself carries a `name` attribute (defaulting to `"TCA"`), letting each usage configure its own prefix — in `Student`, it's overridden to `"SBAI"`.

### `Student` — the commented-out "old way" vs. the active "new way"

```java
@Id
//new way
@RnoId(name = "SBAI") // -> custom id generator annotation

// old way
//    @GenericGenerator(name = "rnoGen", strategy = "com.bhavik.generator.StudentRnoGenerator") <- depricated after hibernate 5
//    @GeneratedValue(generator = "rnoGen")
private String rno;
```

This comment block is contrasting **two different eras of Hibernate's custom-generator API**:

- **The "old way" (commented out):** `@GenericGenerator(name = "rnoGen", strategy = "com.bhavik.generator.StudentRnoGenerator")` paired with `@GeneratedValue(generator = "rnoGen")`. This is the classic Hibernate approach — `@GenericGenerator` registers a named generator by referring to its implementing class **as a string** (`strategy = "..."`), and `@GeneratedValue` then points `@Id` at that named generator. The string-based class reference means no compile-time checking that the class exists or is correctly typed, and this particular form of `@GenericGenerator` was deprecated starting with Hibernate 5 in favor of a cleaner, type-safe alternative.
- **The "new way" (active):** a single custom annotation (`@RnoId`) built on top of Hibernate's `@IdGeneratorType` meta-annotation. Instead of wiring things together with generator names and string class paths, `@IdGeneratorType(StudentRnoGenerator.class)` links the annotation directly to the generator class at compile time (a real `.class` reference, not a string), and `@RnoId(name = "SBAI")` is the whole declaration needed on the field — no separate `@GeneratedValue` required. This is more type-safe, more concise, and is Hibernate's recommended modern pattern for exactly this "write your own ID format" scenario.

## Key takeaways

- When none of JPA's built-in strategies (`IDENTITY`, `SEQUENCE`, `TABLE`, `AUTO`, `UUID`) fit your ID format, implement Hibernate's `IdentifierGenerator` interface and provide your own `generate(...)` logic.
- `@IdGeneratorType` is the modern (post-Hibernate-5) way to wire a custom annotation to a generator class using a real class reference — replacing the older, string-based `@GenericGenerator(strategy = "fully.qualified.ClassName")` pattern, which is deprecated for this use case.
- A custom annotation built on `@IdGeneratorType` can expose its own attributes (like `name` here) so the same generator class can be configured differently per entity or field.
- Because random-suffix generation (`random.nextInt(1000, 9999)`) has no uniqueness guarantee, collisions are theoretically possible with enough inserts — worth keeping in mind if this pattern is extended beyond a learning demo into anything with real collision-sensitivity.
